## The subject route, read back from the portal

**No predecessor in this series has one.** 433-D takes its subject from the RECORD rather than from the form,
so one printed identifier box reaches one of two properties on a declaration the record makes. The
discriminator is an operator input naming no printed cell, and the engine reads its stored value BARE — the
definition carries no `map_option_by_value` — so the option set the portal holds IS the set of spellings the
engine will ever see. It is asserted equal to the branch names the map declares.

| role | input key | property | live type | note |
|---|---|---|---|---|
| discriminator | `433d_subject` | `irs433d_subject` | enumeration/select | options [entity, individual] |
| individual branch | `433d_tin_ssn_itin` | `irs433_tp_ssn_itin` | string/text | reuse, created by 433a |
| entity branch | `433d_tin_ein` | `irs433boi_employer_identification_number` | string/text | reuse, created by 433boi |

**No problem.** The discriminator holds exactly the branches the route declares, both branch properties are live, and the two branches are two distinct properties — which is the whole point: one property serving both would hold an SSN on one filed copy and an EIN on the next, under one name.

## The standing ruling — every reused property names this form, read from the portal

These three were created by earlier passes, so "at create time" for them was a previous cycle.
`hs-provision.mjs` cannot close it — it creates and never patches — so `hs-describe-reused-433d.mjs` patches
descriptions and nothing else. **This section is the portal's answer, not that tool's.**

The patch APPENDS and never replaces. Two of these three carry the backbone convention — "Shared across the
433 series - named for the fact, not the form" — and rewriting that to enumerate forms would erase a
convention to satisfy a later one, which is what [R-21] refuses. The creator attribution and the shared
sentence both stay; this form is added after them.

## The option values, re-asserted from the portal side

`assert-intake-keys.mjs` asserts that every value a DEFINITION emits resolves against the spellings this
form's engine accepts. This asserts the same thing about what the PORTAL actually holds, because the two
can differ: an option silently dropped or renamed at create time leaves a live property whose stored values
the engine cannot resolve, and the definition file still looks right. An enumeration the portal holds with
ZERO options is reported as a problem rather than as a clean pass over an empty set ([R-04]).

18 live option value(s) across 7 enumeration propert(ies) checked in both directions.

**No problem.** Every live option value is translated by its definition, and every value it translates to is a spelling the engine accepts.
